# ARH Step Functions State Machine Explanation

## What is AWS Step Functions?

AWS Step Functions is a managed workflow and orchestration service. It executes a
state machine, where each state performs an action such as invoking a Lambda,
waiting for an external approval, calling another AWS service, branching based on
data, retrying an operation, or ending successfully.

In the ARH PoC, Step Functions controls the workflow around the LangGraph agent.

```text
Input case
   |
   v
Intake Lambda
   |
   v
Manual approval wait
   |
   | SendTaskSuccess: Approved
   v
Execute Lambda
   |
   v
CLOSED / SUCCEEDED
```

The state-machine definition is maintained in:

```text
terraform/modules/langgraph_stepfunctions/state_machine.json.tmpl
```

## ARH state machine

The ARH state machine contains two states:

```text
Intake -> Execute -> End
```

### 1. Intake state

The `Intake` state invokes the intake Lambda using the Step Functions callback
integration:

```json
"Intake": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke.waitForTaskToken",
  "Parameters": {
    "FunctionName": "${intake_arn}",
    "Payload": {
      "case_id.$": "$.case_id",
      "case_text.$": "$.case_text",
      "TaskToken.$": "$$.Task.Token"
    }
  },
  "Next": "Execute"
}
```

The implementation is in:

```text
terraform/modules/langgraph_stepfunctions/state_machine.json.tmpl
```

Step Functions passes three values to the intake Lambda:

| Value | Meaning |
|---|---|
| `case_id` | Case identifier from the workflow input |
| `case_text` | Incoming case text |
| `TaskToken` | Temporary callback token generated by Step Functions |

The `.$` suffix means that the value is read from the Step Functions JSON input.
For example, an execution can start with:

```json
{
  "case_id": "CASE-001",
  "case_text": "A request was submitted to update group contacts."
}
```

The intake Lambda receives those values plus the task token.

## What happens inside the Intake Lambda?

The intake Lambda implements the LangGraph-style agent loop. It:

1. Creates the initial graph state.
2. Persists the state in DynamoDB.
3. Selects the next tool.
4. Calls the mock DataPower Lambda.
5. Adds the tool result to the graph history.
6. Persists the updated state.
7. Repeats until `create_decision_task` is selected.

The implementation is in:

```text
terraform/files/langgraph_lambda.py
```

In Bedrock mode, the flow is:

```text
LangGraph Lambda
   |
   v
Bedrock Converse selects next tool
   |
   v
Mock DataPower Lambda executes tool
   |
   v
Graph state saved to DynamoDB
```

The Bedrock-selected intake sequence in the PoC was:

```text
extract_fields
retrieve_sop
run_validations
search_similar_cases
create_decision_task
```

After `create_decision_task`, the Lambda stores the task token in DynamoDB and
returns a pending result:

```json
{
  "case_id": "CASE-001",
  "task_id": "TASK-123",
  "status": "PENDING"
}
```

The execution is then paused by Step Functions.

## Why does `waitForTaskToken` matter?

`waitForTaskToken` creates the human-approval boundary. It instructs Step
Functions to invoke the Lambda but not continue to the next state until a caller
uses the task token to send a callback.

While waiting, the execution remains:

```text
RUNNING
```

The workflow does not continue merely because the Lambda returned
`status: PENDING`. An external system, approval service, or human-driven script
must call `SendTaskSuccess` or `SendTaskFailure` using the token.

Example approval payload:

```json
{
  "case_id": "CASE-001",
  "decision": "Approved"
}
```

After `SendTaskSuccess`, Step Functions moves from:

```text
Intake -> Execute
```

This boundary is enforced by Step Functions infrastructure. The model cannot
skip it.

## 2. Execute state

After approval, the `Execute` state invokes the execute Lambda:

```json
"Execute": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke",
  "Parameters": {
    "FunctionName": "${execute_arn}",
    "Payload": {
      "case_id.$": "$.case_id",
      "decision.$": "$.decision"
    }
  },
  "End": true
}
```

The execute Lambda receives:

```json
{
  "case_id": "CASE-001",
  "decision": "Approved"
}
```

It then:

1. Loads the saved graph state from DynamoDB.
2. Calls `execute_transaction` when the decision is approved.
3. Calls `write_audit_record`.
4. Saves the final state.
5. Returns `status: CLOSED`.

For an approved case, the final result is:

```json
{
  "case_id": "CASE-001",
  "decision": "Approved",
  "status": "CLOSED"
}
```

Step Functions then marks the execution:

```text
SUCCEEDED
```

## Complete execution flow

```text
1. StartExecution
   Input:
   {
     "case_id": "CASE-001",
     "case_text": "A request was submitted to update group contacts."
   }

2. Step Functions enters Intake.

3. Intake Lambda receives the case data and task token.

4. Intake Lambda:
   - Calls Bedrock to select tools when USE_BEDROCK=true.
   - Invokes mock tools.
   - Saves graph state to DynamoDB.
   - Creates the decision task.
   - Saves the task token to DynamoDB.

5. Step Functions pauses at waitForTaskToken.

6. An approval system or operator calls SendTaskSuccess with decision=Approved.

7. Step Functions enters Execute.

8. Execute Lambda:
   - Calls execute_transaction.
   - Calls write_audit_record.
   - Saves final state.

9. Step Functions returns status=CLOSED.

10. Execution status becomes SUCCEEDED.
```

## Step Functions versus LangGraph

The two components have different responsibilities:

| Component | Responsibility |
|---|---|
| LangGraph logic | Selects tools, maintains tool history, calls Bedrock, persists graph state |
| Step Functions | Controls the high-level workflow and approval pause |
| Intake Lambda | Runs the graph before approval |
| Execute Lambda | Runs transaction and audit steps after approval |
| DynamoDB | Stores graph state and task token |
| Bedrock | Selects the next tool when `USE_BEDROCK=true` |

The key architectural separation is:

```text
Bedrock decides which tool to call.
Step Functions decides whether execution may continue.
```

This makes the LangGraph design more reliable for human approval than a
prompt-only boundary. Even if the model selects tools dynamically, it cannot
bypass the Step Functions callback wait.
